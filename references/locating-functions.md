# 函数定位实战（Step 3 详解）

四种方法的完整 IDA / Ghidra 操作步骤，按推荐顺序。

**总原则**：先用最快的方法覆盖 80%，剩下的用最稳的方法啃。

---

## 方法 0：先确认「低地址基础库没变」（花 20 分钟，省半天）

**在动手定位之前先做这个。**

微信的低地址区（`0x0` – `0x100000` 附近）放的是基础工具函数：内存分配、容器操作、字符串处理、序列化。**这些跨版本几乎不变。**

helper 项目里已确认长期稳定的一批：

```
0x2010
0x7a60
0x45d10
0x88ad0
```

### 操作

```powershell
# 对每个低地址，比对旧新版的前 32 字节
py -3.13 sig_extract.py --dll old.dll --rva 0x7a60 --len 32
py -3.13 sig_extract.py --dll new.dll --rva 0x7a60 --len 32
```

两次输出完全一致 → **地址没变，直接写 `case 0x7a60: return 0x7a60;`，跳过定位**。

### 为什么值得先做

一次适配里「地址完全没动」的条目通常占 **30–50%**。先把这批勾掉，剩下的工作量直接砍半。

### 判据

必须同时满足：

1. 函数大小相同（`fn_end - fn_start`）
2. 前 32 字节逐字节相同

**任意一条不满足就老老实实定位**——可能是函数被重排了，只是巧合地址相同。

## 方法 A：Diaphora 自动比对（首选，覆盖 80%）

### 为什么首选

两个版本 90% 的代码是同一批函数，只是地址变了。Diaphora 用「控制流图 + 常量 + 调用关系 + 字符串引用」多维特征做匹配，能自动给你「旧地址 ↔ 新地址」对照表。

### IDA 版操作步骤

**准备**：把两个版本的 `Weixin.dll` 分别拷到一个短路径下的独立目录（IDA 分析大文件对路径敏感，中文路径容易出问题）。

```
D:\work\wechat-41556\Weixin.dll
D:\work\wechat-42011\Weixin.dll
```

**第 1 步 — 建旧库**

```
1. IDA 打开 D:\work\wechat-41556\Weixin.dll
2. 等 auto-analysis 完成（进度条消失 + 状态栏 "AU: idle"）
3. File > Produce file > Create DIF file
   → 选 D:\work\wechat-41556\Weixin.sqlite
4. 等导出完成（几 GB 的 DLL 要 20–60 分钟）
```

**第 2 步 — 建新库**

```
1. IDA 打开 D:\work\wechat-42011\Weixin.dll，等分析完
2. File > Produce file > Create DIF file  ← 这一步可以跳
3. 直接：Plugins > Diaphora > Diff database
4. 选 D:\work\wechat-41556\Weixin.sqlite
5. 等比对完成（又是一轮长时间）
```

**第 3 步 — 读结果**

Diaphora 结果窗口按 `similarity` 降序排列：

| 相似度 | 可信度 | 处理 |
|---|---|---|
| 1.00 | 几乎确定同一函数 | 直接采信 |
| 0.95 – 0.99 | 高度可信 | 抽查几个确认 |
| 0.70 – 0.95 | 可能对也可能错 | **必须逐个验证** |
| < 0.70 | 不可信 | 当没匹配上处理 |

**导出对照表**：结果窗口右键 > `Export to CSV`，得到 `address_best, address_partial` 两列，就是新旧地址。

**第 4 步 — 只保留你需要的**

Diaphora 会匹配十几万个函数，你只需要那 54 个（39 文本 + 15 朋友圈）。做法：

1. 打开旧库，从 `core_version.h` 里读 54 个旧 RVA
2. 在 CSV 里查这 54 个旧地址对应的新地址
3. 查不到的就是「没匹配上」，进方法 B/C/D

### Ghidra 版操作步骤（免费替代）

```
1. 新建 Ghidra 项目，导入两个 Weixin.dll（分两个文件夹）
2. 每个 program 上右键 > Analyze，等完成
3. Tools > Version Tracking
4. 新建 session
5. Add program（旧的）→ Set as Source
6. Add program（新的）→ Set as Destination
7. 跑 correlators（默认全选，至少要有：
   - Exact Function Bytes
   - Exact Function Instructions
   - Function Reference
   - Symbol Name）
8. 结果窗口看 Matches / Accepted / Rejected 三个 tab
9. 选中匹配较好的，右键 > Accept
10. 导出：File > Export > Version Tracking Matches
```

**Ghidra 的优势**：完全免费，且 correlator 可配置性强，能自己写匹配器。

**劣势**：大 DLL 分析比 IDA 慢，内存占用高（16 GB 内存要调大 `analyzeHeadless` 的 `-Xmx`）。

## 方法 B：特征码扫描（覆盖剩下的，最通用）

### 什么时候用

- Diaphora 没匹配上（函数被优化、拆分、内联）
- 只有旧版本的一个函数，新版本还没分析

### 第 1 步 — 提特征码

```powershell
py -3.13 "$env:USERPROFILE\.agents\skills\wechat-version-port\scripts\sig_extract.py" `
  --dll "D:\work\wechat-41556\Weixin.dll" --rva 0x2fb010 --len 48
```

输出：
```
# RVA 0x2fb010  (48 字节，通配 4 处)
48 89 5C 24 08 55 56 57 41 54 48 8B 05 ?? ?? ?? ?? E8 ?? ?? ?? ??
```

**看懂这串**：

| 字节 | 含义 | 是否通配 |
|---|---|---|
| `48 89 5C 24 08` | `mov [rsp+8], rbx`（函数序言） | ✗ 保留 |
| `55 56 57` | `push rbp/rsi/rdi` | ✗ 保留 |
| `41 54` | `push r12` | ✗ 保留 |
| `48 8B 05 ?? ?? ?? ??` | `mov rax, [rip+disp32]` | ✓ disp32 通配 |
| `E8 ?? ?? ?? ??` | `call rel32` | ✓ rel32 通配 |

### 第 2 步 — 在新版本里搜

```powershell
py -3.13 "$env:USERPROFILE\.agents\skills\wechat-version-port\scripts\sig_scan.py" `
  --dll "D:\work\wechat-42011\Weixin.dll" `
  --pattern "48 89 5C 24 08 55 56 57 41 54 48 8B 05 ?? ?? ?? ?? E8 ?? ?? ?? ??"
```

### 第 3 步 — 按结果调整

| 结果 | 原因 | 处理 |
|---|---|---|
| **恰好 1 处** | 合格 | 记录 RVA，进 Step 4 验证 |
| **0 处** | 特征段被优化（函数被拆、序言被改、被内联） | ① 加到 64 或 80 字节 ② 换个位置提（比如函数中部） ③ 换方法 C |
| **> 1 处** | 特征太短或太通用 | ① 往后多取 16 字节 ② 挑一段更有辨识度的指令（比如带特定常量的） |

### 特征码设计原则

**好的特征**：

```
48 83 EC 28              sub rsp, 0x28           ← 序言，稳定
41 B8 00 10 00 00        mov r8d, 0x1000          ← 特定常量，高辨识度
48 8D 15 ?? ?? ?? ??     lea rdx, [rip+xxx]       ← 字符串引用
B9 20 00 00 00           mov ecx, 0x20            ← 特定常量
```

**坏的特征**：

```
48 89 5C 24 08           mov [rsp+8], rbx         ← 到处都是
48 83 EC 28              sub rsp, 0x28            ← 全篇都是
FF 15 ?? ?? ?? ??        call [rip+xxx]           ← 通用调用
```

**经验值**：20–40 字节，含至少 2 个「非通用」元素（特定常量 / 字符串引用 / 特殊指令组合）。

### 特殊技巧：不用序言，用函数中段

如果函数序言被优化掉，从函数中部提：

```powershell
# 先从旧版看函数体，找一个有特色的指令序列的 RVA
py -3.13 sig_extract.py --dll old.dll --rva 0x2fb180 --len 40
```

中段往往比序言更有辨识度（比如包含 `cmp` 特定值、`lea` 特定字符串）。

## 方法 C：字符串交叉引用（最稳，优先用于「有字符串」的函数）

### 为什么最稳

字符串内容几乎不随版本变化。`"撤回了一条消息"` 在 4.1 和 4.2 里都是这几个字，只是引用它的代码位置变了。

### IDA 操作

**第 1 步 — 旧版本定位字符串**

```
1. 跳到旧函数（G 键，输入 0x2fb010）
2. 函数体里找 `lea rdx, aXxx` / `lea rcx, aYyy`
3. 双击那个 aXxx → 跳到字符串定义处，记下内容
```

**第 2 步 — 新版本搜字符串**

```
1. 切到新版本的 IDA
2. Alt+B（Search > Sequence of bytes）
   或 Search > Text（直接搜字符串内容）
3. 输入字符串内容，比如 "撤回了一条消息"
4. 找到结果后，双击跳到定义处
5. 按 X（xrefs to）看谁引用它
```

**第 3 步 — 从 xref 找函数**

xref 列表里会显示 `sub_XXXXXXX+偏移`，那个 `sub_XXXXXXX` 就是同一函数的新地址。

**中文字符串的处理**：

微信里大部分字符串是 **UTF-16LE**（宽字符）。

搜的时候要么：
- IDA 里选 `Search > Text`，并勾选 `Unicode`
- 或者算 UTF-8/UTF-16 的字节序列用 `Alt+B` 搜

```python
# 算 UTF-16LE 字节
s = "撤回了一条消息"
print(" ".join(f"{b:02X}" for b in s.encode("utf-16-le")))
```

### Ghidra 操作

```
1. Search > For Strings，输入内容
2. 结果列表双击
3. 在 Listing 里右键字符串 > References > Show References to Address
4. 找到引用它的函数
```

### 适合用字符串定位的功能

| 功能 | 典型字符串 |
|---|---|
| 发消息 | `"发送失败"` / `"消息已发出"` |
| 撤回 | `"撤回了一条消息"` / `"你撤回了一条消息"` |
| 好友申请 | `"请求添加你为朋友"` |
| 群成员 | `"加入了群聊"` / `"退出了群聊"` |
| 朋友圈 | 各种 URL 常量 |
| 登录状态 | `"当前设备已离线"` |

## 方法 C2：vtable → RTTI → 构造函数（C++ 类成员首选）

**这是 helper 项目定位工厂函数 `0x6f4c70` 的实际方法。**

### 什么时候用

- 目标是某个 C++ 类的成员函数
- 要定位「创建某类对象的工厂函数」
- 目标函数无字符串、特征也不稳

### 原理

C++ 类实例的第一个字段是 vtable 指针。一个类的**虚函数数量、顺序**在版本间几乎不变，只有地址变。所以：

```
已知旧 vtable 的某个槽位
  → 在新版本里找同样的 vtable 结构
  → 从新 vtable 取槽位
  → 拿到新地址
```

比代码特征匹配可靠得多。

### 步骤 A：已知某个旧函数，求新地址

```
1. 旧版本：看旧函数属于哪个类
   - 在 IDA 里看函数的 this 指针（rcx）用法
   - 或函数名上有类名（IDA 会标 ClassName::Method）
2. 找到该类的 vtable 地址（旧版本）
   - 在 IDA 的 Structures 或 Names 里搜 `vtable_ClassName`
   - 或找构造函数里 `mov [reg], <vtable>` 的指令
3. 记下 vtable 里目标函数的槽位索引
4. 新版本：搜 vtable 的地址值（8 字节小端序列）
   - 因为新版本的 vtable 里存的是新的函数指针
   - 但 vtable 本身的位置变了，不能直接搜
   → 改用：搜「同时包含多个旧 vtable 成员地址相对位置」的序列
   → 或用 Diaphora 匹配构造函数，再读 vtable
5. 从新 vtable 取同一槽位 = 新地址
```

**关键难点**：vtable 内容全变了，不能直接搜地址。**实际做法是通过构造函数反查**——先定位构造函数（构造函数里有 vtable 地址的立即数，且调 operator new），再读它写的 vtable。

### 步骤 B：从零定位一个工厂函数

工厂函数 `CreateXxx` 的特征：调 `operator new` → 往对象头写 vtable → 返回。

```
1. 找到目标类的 vtable RVA（新版）
   来源：已知的 vtable 地址在映射表里（如 0x8e53588）

2. 搜「把该 vtable 地址写进对象」的指令序列：
      lea rax, [rip+<vtable>]
      ...
      mov [rbx], rax         ← 写 vtable 到对象 offset 0
   这条指令所在函数 = 构造函数

3. 构造函数的所有调用者里，含 operator new 调用的那个 = 工厂函数
```

### 实例：`0x6f4c70` 在 4.2.0.11 的定位

helper 的做法（推断，从 diff 反推）：

```
旧版 4.1.15.56  工厂 0x6f4c70
  ↓ 通过它构造的对象的 vtable 反查
  ↓ 确认构造函数特征（operator new 分配大小 + 写 vtable + 字段初始化）
  ↓ 在新版搜同样的构造函数
  ↓ 从构造函数往上找调用者（工厂）
新版 4.2.0.11  工厂 0x71c4e0
```

### 副产品：顺便拿到结构体信息

定位构造函数时，顺手能拿到：

- `operator new` 的分配大小 → **结构体大小判据**（见 SKILL.md Step 4）
- 各字段的写入偏移 → **结构体布局**

**所以定位工厂函数这一步，同时解决了地址和结构体两件事。**

### 把调用链记在注释里

helper 的 `native/friend_request.h` 直接记录：

```
// 1780cd0 → 754330 → 1a26440 → 1a17980
```

**照做。** 下次适配时这些链是宝贵资产，不用重新捋。

## 方法 D：调用图回溯（用于「既无字符串、特征也不稳」的函数）

### 思路

单个函数定位不了，但它的调用者和被调用者能定位。

```
已知：A → B → C
能定位 A（有字符串）
能定位 C（有字符串）
求 B
```

### IDA 操作

**第 1 步 — 定位 A 和 C**（用方法 B 或 C）

**第 2 步 — 在 A 里找 call**

```
1. 跳到 A 的新地址
2. 从上往下扫 call 指令
3. 每个 call 的目标都是一个候选函数
```

**第 3 步 — 在 C 里找调用者**

```
1. 跳到 C 的新地址
2. 在函数名上按 X（xrefs to）
3. 列表里所有 `sub_XXX+偏移` 都是调用 C 的函数
```

**第 4 步 — 取交集**

既在 A 的 call 列表里、又在 C 的 caller 列表里的函数 = B。

### 实操建议

微信里典型的三层调用链：

```
消息分发器
  └─ 消息解析
      └─ 各类型处理（文本/图片/文件/语音）
```

**先定位分发器和最末端的处理函数**（都有字符串），中间层用交集法。

### 4.2 朋友圈为什么必须用这个方法

朋友圈的 `core_moments_address()` 有 15 条映射，且地址体系和主逻辑完全不同。原因：

- 朋友圈走的是独立的 RPC 通道
- 涉及的函数大多不碰可见字符串（数据是 protobuf 序列化的）
- 特征码辨识度低（大量相似的序列化代码）

只能靠「已知入口 + 已知出口 + 中间回溯」一节节捋。

## 定位完的验证（**必做，别跳**）

找到地址不等于找对函数。三步验证：

### 验证 1：函数大小相近

```powershell
# IDA 里看函数尾地址 - 首地址
# 新旧版本大小差超过 20% → 可疑
```

### 验证 2：调用关系一致

```
1. 旧函数调用了哪些函数？（记下 3–5 个有名字的，比如 memcpy、某个虚函数）
2. 新函数是否也调用这些？
3. 结构不一致 → 大概率找错了
```

### 验证 3：字符串引用一致

```
1. 旧函数引用了哪些字符串？
2. 新函数是否引用同样的？
```

**三条都过 → 采信。任意一条不过 → 回方法 A/C 重来。**

## 效率建议

| 阶段 | 方法 | 覆盖 | 耗时 |
|---|---|---|---|
| 0 | 低地址基础库比对（大概率没变） | 30–50% 条目 | 20 分钟 |
| 1 | Diaphora 全量比对 | 剩余中的 70–85% | 4–8 小时（大部分是等） |
| 2 | 字符串 xref | 再 10% | 2–4 小时 |
| 3 | 特征码扫描 | 再 4% | 2–4 小时 |
| 4 | vtable → 构造函数 | 类成员 / 工厂函数 | 1–3 小时 |
| 5 | 调用图回溯 | 最后 1% | 4–8 小时（最费脑） |
| 6 | 逐条验证（大小 / 调用关系 / 字符串引用） | 全部 | 2–4 小时 |

**以 4.2.0.11 的 45 条映射为例：总计 15–30 小时**，纯定位时间，不含实测。

**先做阶段 0 的意义**：如果 30–50% 的地址没变，后面所有阶段的基数直接砍半。20 分钟换 8 小时。

## 一个常被忽略的加速手段

**先只适配「文本收发」这一条链路，跑通上线，再补其他。**

理由：

- 文本收发只涉及 10–15 个函数（相比 45 个）
- 能跑起来就能验证整套流程是通的
- 用户最需要的也是文本
- 作者本人就是这个路径：`1d40bc1` 先开放收发，**26 分钟后** `3e65e4b` 才补好友和群事件

**别一开始就想支持全部功能**，那样两周都在定位，没有任何可验证的中间成果。

helper 有三次与版本适配直接相关的提交，**按时间顺序看思路最清晰**：

```powershell
cd C:\helper-main

# ① 4.1.15.56：把框架搭起来（55 条映射 + core_address 封装）

# ② 4.2.0.11：有了框架后加一个版本（40 条）
git show 1d40bc1 -- native/

# ③ 26 分钟后的补漏（5 条，好友验证链路）
```

| 提交 | 学习重点 |
|---|---|

4. 和仓库里的映射对答案
